# Практика: C4 System Context Diagram (4 ситуации)

**Задача (для каждой ситуации):**
1. Определить систему в фокусе и дать ей название.
2. Определить людей и внешние системы.
3. Определить взаимодействия и подписать смыслом.
4. Провести Boundary и построить диаграмму.
5. Проверить по чек-листу; если Boundary ошибочна — исправить.

**Чек-лист**, применённый к каждой из 4 диаграмм:

- [ ] Название системы в фокусе конкретное, а не «Система вообще».
- [ ] Actors — реальные роли, а не обобщённый «пользователь».
- [ ] Внешние системы — конкретно те, что названы в «что уже существует»; ничего не выдумано без пометки допущения.
- [ ] Каждая связь подписана смыслом и бизнес-намерением, а не «использует».
- [ ] На диаграмме ровно один System-бокс в фокусе — без внутренней декомпозиции (это context, не container diagram).
- [ ] Внутрь Boundary попадает **только** создаваемая система; всё, что уже существует, — снаружи, даже если тесно интегрировано.
- [ ] Если в тексте явно сказано, что актор/система НЕ взаимодействует с новой системой напрямую — на диаграмме нет прямой стрелки между ними.

## Ситуация 1. Запись в университетские лаборатории

**Система в фокусе:** «Система бронирования лабораторий» — отвечает за показ доступного времени, приём заявок, проверку конфликтов с обязательными занятиями и уведомление о результате.

| Тип | Название | Роль в контексте |
|---|---|---|
| Actor | Пользователь (студент/сотрудник) | Смотрит доступное время, подаёт заявку на бронь |
| External system | Университетская информационная система | Данные о студентах/сотрудниках (кто обращается) |
| External system | Система расписания занятий | Обязательные занятия — источник конфликтов при проверке брони |
| External system | Почтовый сервис | Доставка уведомления о результате брони |
| External system | Система карточного доступа | Физический доступ в лабораторию после подтверждения |

**Взаимодействия:**

| Откуда | Куда | Смысл |
|---|---|---|
| Пользователь | Система бронирования | Смотрит слоты, подаёт заявку |
| Система бронирования | Пользователь | Показывает статус и результат брони |
| Система бронирования | Университетская информационная система | Проверяет, кто обращается (студент/сотрудник) |
| Система бронирования | Система расписания занятий | Получает обязательные занятия для проверки конфликта слота |
| Система бронирования | Почтовый сервис | Инициирует письмо с результатом брони |
| Система бронирования | Система карточного доступа | Передаёт разрешение на вход в лабораторию на время брони |

```plantuml
@startuml Situation1
skinparam backgroundColor transparent
skinparam componentStyle rectangle

actor "Пользователь\n(студент/сотрудник)" as User

rectangle "Граница системы" {
  component "Система бронирования\nлабораторий" as Focus
}

component "Университетская\nинформационная система" as UIS
component "Система расписания\nзанятий" as Schedule
component "Почтовый сервис" as Mail
component "Система карточного\nдоступа" as Access

User --> Focus : смотрит слоты,\nподаёт заявку
Focus --> User : статус и результат брони
Focus --> UIS : проверяет данные пользователя
Focus --> Schedule : получает обязательные занятия
Focus --> Mail : инициирует письмо с результатом
Focus --> Access : передаёт разрешение на доступ
@enduml
```

**Проверка / ловушка Boundary:** легко случайно "затащить" внутрь границы систему расписания или УИС, потому что решение о брони логически от них зависит — но обе системы существуют независимо и лишь **опрашиваются**, значит остаются снаружи. Допущение: кто именно подтверждает бронь — сама система по правилам или лаборант вручную — в кейсе не указано; на диаграмме заложена автоматическая проверка (без отдельного актора-администратора), так как в списке функций явного человека-утверждающего нет.

## Ситуация 2. Запись пациента в частную клинику

**Система в фокусе:** «Сервис онлайн-записи к врачу» — поиск врача и времени, запись на слот, оплата при необходимости, подтверждение и напоминание.

| Тип | Название | Роль в контексте |
|---|---|---|
| Actor | Пациент | Ищет врача, записывается, при необходимости оплачивает |
| External system | Медицинская информационная система клиники | Источник расписания врача; получает данные о новой записи |
| External system | Внешний платёжный сервис | Проведение оплаты приёма |
| External system | Сервис SMS-рассылок | Доставка подтверждения и напоминания пациенту |

**Взаимодействия:**

| Откуда | Куда | Смысл |
|---|---|---|
| Пациент | Сервис онлайн-записи | Ищет врача и слот, оформляет запись |
| Сервис онлайн-записи | Медицинская информационная система | Запрашивает доступное время врача |
| Сервис онлайн-записи | Медицинская информационная система | Передаёт данные о новой записи (чтобы врач увидел её в своей системе) |
| Сервис онлайн-записи | Внешний платёжный сервис | Инициирует оплату приёма |
| Внешний платёжный сервис | Сервис онлайн-записи | Подтверждает статус оплаты |
| Сервис онлайн-записи | Сервис SMS-рассылок | Инициирует подтверждение и напоминание |
| Сервис SMS-рассылок | Пациент | Доставляет SMS |

```plantuml
@startuml Situation2
skinparam backgroundColor transparent
skinparam componentStyle rectangle

actor "Пациент" as Patient

rectangle "Граница системы" {
  component "Сервис онлайн-записи\nк врачу" as Focus
}

component "Медицинская информационная\nсистема клиники" as MIS
component "Внешний платёжный\nсервис" as Pay
component "Сервис SMS-рассылок" as SMS

Patient --> Focus : ищет врача, выбирает\nслот, записывается
Focus --> MIS : запрашивает доступное время врача
Focus --> MIS : передаёт данные о новой записи
Focus --> Pay : инициирует оплату приёма
Pay --> Focus : подтверждает статус оплаты
Focus --> SMS : инициирует подтверждение\nи напоминание
SMS --> Patient : доставляет SMS
@enduml
```

**Проверка / ловушка Boundary:** в кейсе прямо сказано — «врач продолжает работать в существующей медицинской системе», то есть **врач не является актором новой системы**. Главная ошибка, которую нужно не допустить, — нарисовать стрелку «Врач → Сервис записи»: её на диаграмме нет и не должно быть. Также ошибкой было бы завести собственный календарь врача внутри нового сервиса — МИС остаётся единственным источником истины о расписании.

## Ситуация 3. Корпоративная заявка на оборудование

**Система в фокусе:** «Система заявок на оборудование» — создание заявки, статус, передача в IT-службу, проверка доступности, уведомление о решении.

| Тип | Название | Роль в контексте |
|---|---|---|
| Actor | Сотрудник | Создаёт заявку, смотрит статус, получает решение |
| Actor | Руководитель | Согласовывает или отклоняет заявку |
| Actor | Сотрудник IT-службы | Получает согласованную заявку и выдаёт оборудование |
| External system | Кадровая информационная система | Оргструктура: кто чей руководитель |
| External system | Складская учётная система | Наличие оборудования на складе |
| External system | Корп. система единого входа (SSO) | Аутентификация сотрудника и руководителя |
| External system | Корпоративная почта | Доставка уведомлений о решении |

**Взаимодействия:**

| Откуда | Куда | Смысл |
|---|---|---|
| Сотрудник | Система заявок | Создаёт заявку на оборудование |
| Система заявок | Кадровая информационная система | Определяет руководителя сотрудника |
| Система заявок | Руководитель | Направляет заявку на согласование |
| Руководитель | Система заявок | Согласовывает / отклоняет заявку |
| Система заявок | Складская учётная система | Запрашивает наличие оборудования |
| Складская учётная система | Система заявок | Возвращает данные о доступности |
| Система заявок | Сотрудник IT-службы | Передаёт согласованную заявку на исполнение |
| Система заявок | Корпоративная почта | Инициирует уведомление сотруднику о решении |
| Система заявок | Корп. система единого входа | Аутентифицирует пользователей системы |

```plantuml
@startuml Situation3
skinparam backgroundColor transparent
skinparam componentStyle rectangle

actor "Сотрудник" as Employee
actor "Руководитель" as Manager
actor "Сотрудник IT-службы" as ITStaff

rectangle "Граница системы" {
  component "Система заявок\nна оборудование" as Focus
}

component "Кадровая\nинформационная система" as HR
component "Складская учётная\nсистема" as Warehouse
component "Корп. система\nединого входа (SSO)" as SSO
component "Корпоративная почта" as Mail

Employee --> Focus : создаёт заявку, смотрит статус
Focus --> HR : определяет руководителя сотрудника
Focus --> Manager : направляет заявку на согласование
Manager --> Focus : согласовывает / отклоняет
Focus --> Warehouse : запрашивает наличие оборудования
Warehouse --> Focus : возвращает данные о доступности
Focus --> ITStaff : передаёт согласованную заявку
Focus --> Mail : уведомляет сотрудника о решении
Focus --> SSO : аутентифицирует пользователей
@enduml
```

**Проверка / ловушка Boundary:** «Складская учётная система» и «IT-служба» — разные сущности: склад лишь **отдаёт данные о наличии**, а физическую выдачу выполняют **люди** из IT-службы; их легко случайно объединить в одну связь. Также не названа отдельная система для IT-службы (тикет-система не упомянута в «что уже существует»), поэтому IT-служба смоделирована как актор (человек/отдел), а не как внешняя система — это допущение, отдельно зафиксировано.

## Ситуация 4. Сервис выдачи заказов в пункте выдачи

**Система в фокусе:** «Система выдачи заказов» — получает сведения о заказах в пункте, ищет заказ, фиксирует факт выдачи, сообщает в интернет-магазин, инициирует уведомление клиенту.

| Тип | Название | Роль в контексте |
|---|---|---|
| Actor | Сотрудник пункта выдачи | Ищет заказ, выдаёт его, фиксирует факт выдачи |
| External system | Основной интернет-магазин | Источник данных о заказе; получатель факта выдачи |
| External system | Система склада | Данные о местонахождении товара в пункте |
| External system | Система курьерской службы | Сообщает о прибытии заказа в пункт |
| External system | Внешний сервис SMS-уведомлений | Доставляет уведомление клиенту |

**Взаимодействия:**

| Откуда | Куда | Смысл |
|---|---|---|
| Сотрудник пункта выдачи | Система выдачи | Ищет заказ по номеру/данным клиента, фиксирует выдачу |
| Система курьерской службы | Система выдачи | Сообщает о поступлении заказа в конкретный пункт |
| Основной интернет-магазин | Система выдачи | Передаёт данные заказа (товар, покупатель) |
| Система выдачи | Система склада | Уточняет местонахождение товара в пункте |
| Система выдачи | Основной интернет-магазин | Передаёт факт выдачи заказа |
| Система выдачи | Внешний сервис SMS-уведомлений | Инициирует уведомление о поступлении |
| Внешний сервис SMS-уведомлений | Покупатель | Доставляет SMS о поступлении заказа |

```plantuml
@startuml Situation4
skinparam backgroundColor transparent
skinparam componentStyle rectangle

actor "Сотрудник пункта\nвыдачи" as Staff
actor "Покупатель" as Customer

rectangle "Граница системы" {
  component "Система выдачи\nзаказов" as Focus
}

component "Основной\nинтернет-магазин" as Shop
component "Система склада" as Warehouse
component "Система курьерской\nслужбы" as Courier
component "Внешний сервис\nSMS-уведомлений" as SMS

Staff --> Focus : ищет заказ, фиксирует выдачу
Courier --> Focus : сообщает о поступлении заказа
Shop --> Focus : передаёт данные заказа
Focus --> Warehouse : уточняет местонахождение товара
Focus --> Shop : передаёт факт выдачи
Focus --> SMS : инициирует уведомление
SMS --> Customer : доставляет SMS
@enduml
```

**Проверка / ловушка Boundary:** в кейсе прямо сказано — «покупатель напрямую с интерфейсом новой системы не работает». Главная ошибка — провести стрелку «Покупатель → Система выдачи»: её быть не должно. Покупатель появляется на диаграмме только как получатель SMS от внешнего сервиса уведомлений, что и отражает эту границу.

## Итоговое наблюдение по всем 4 диаграммам

Общая закономерность ошибок, которую проверяет этот чек-лист: в двух ситуациях из четырёх (2 и 4) кейс **явно исключает** очевидного на первый взгляд участника (врача, покупателя) из числа акторов новой системы — это главная проверка на корректность Boundary. В ситуациях 1 и 3 риск другой — случайно затащить внутрь границы внешнюю систему, которая лишь предоставляет данные (расписание, склад), вместо того чтобы оставить её снаружи как источник интеграции.
